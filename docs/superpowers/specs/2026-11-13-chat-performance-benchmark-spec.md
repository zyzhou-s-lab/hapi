# HAPI 消息列表性能对比测试清单与输出表格规范

本文档定义了 HAPI Web 会话消息页在大历史会话下的 **10 项端到端浏览器性能测试项目**、**统一采集口径**、**标准输出表格模板**，以及 `main` (`c82066b0`) 与 `hapi-answer-in-grid` (`a9ead09a`) 在 4 个真实大型会话上的实测基线数据。

---

## 一、测试环境与标准操作流程

### 1. 环境前置条件
- **浏览器与视口**：Playwright Chromium 无头/有头实例，统一移动端视口 `412 × 915`（模拟高频手机远程控制场景，触发紧凑布局与虚拟滚动边界）。
- **后端数据源**：连接同一实例的 Hub 服务（如 `http://127.0.0.1:3006`），确保对比分支读取完全相同的 SQLite 会话历史数据。
- **被测样本要求**：选择至少 3~4 个真实大体积会话（单会话原始消息 JSON 在 `750 KB ~ 14 MB` 之间，包含多轮工具调用、代码块及长文本回复）。

### 2. 标准化单次测试动作序列
每个会话在每个分支独立新建干净的 Browser Context，按以下固定三步执行：
1. **冷启动打开会话（Phase A：首屏加载与渲染）**
   - 页面直接导航至 `/sessions/<sessionId>`。
   - 自动完成 Token 登录换取 JWT（记录代码启动到认证完成耗时）。
   - 等待首屏消息拉取并渲染出最后一条回复的文本节点，且 `requestAnimationFrame` 连续 2 帧稳定（记录首屏拉取+渲染耗时、首屏 DOM 节点数、首屏 JS 内存、首屏压缩下载体积）。
2. **连续向上滚动与历史分页加载（Phase B：滚动与增补历史）**
   - 在聊天滚动容器上执行定速连续向上滚轮操作（每次 `wheel(0, -900)`，间隔 `120 ms`，共执行 18~20 次），触发顶部 `loadMore` 历史分页拉取与前置插入（`prepend-history`）。
   - 实时通过 `requestAnimationFrame` 采样每一帧的帧间隔（计算 P95 帧间隔与最长单帧卡顿耗时）。
3. **滚动后稳态采集（Phase C：峰值与总量结算）**
   - 向上滚动及历史分页加载完成后等待 `600 ms` 稳态，采集最终 DOM 节点数、全程峰值 JS 内存、全程累计主线程阻塞时长（Long Tasks）、长任务次数，以及累计消息接口下载体积。

## 二、10 项性能测试指标定义与采集口径

| 序号 | 测试项名称（表格展示名） | 单位 | 采集口径与计算方式 | 评判方向 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **刷新到最后一条回复出现** | `s` | 从 `navigationStart`（页面开始加载）到会话最后一条回复内容挂载进 DOM 且完成绘制的总耗时（等于第 2 项 + 第 3 项）。 | 越小越好 |
| **2** | `↳ 其中：加载前端代码到登录完成` | `s` | 从页面启动到 `POST /api/auth` 响应返回并写入认证状态的耗时（反映静态包加载与鉴权开销，通常作为对照基准）。 | 越小越好 |
| **3** | `↳ 其中：拉取数据 + 渲染出对话` | `s` | 从登录完成、发起 `/api/sessions/:id/messages` 请求开始，到最后一条回复渲染上屏的耗时（核心反映首屏数据归约与首屏组件树挂载效率）。 | 越小越好 |
| **4** | **主线程卡顿总时长** | `s` | 通过 `PerformanceObserver({ type: 'longtask' })` 采集从页面打开到滚动结束全过程中，所有耗时 `> 50ms` 任务的持续时间总和（Total Long Task Duration）。 | 越小越好 |
| **5** | **超过 50ms 的长任务数** | `次` | 全程触发浏览器 Long Task（单次霸占主线程超过 `50 ms`，会导致掉帧或点击无响应）的总次数。 | 越小越好 |
| **6** | **页面 DOM 节点数（首屏 → 向上滚动后）** | `个` | 首屏渲染完成时的 `document.querySelectorAll('*').length` $\to$ 连续向上滚动并加载历史分页后的 `document.querySelectorAll('*').length`。反映虚拟列表回收与折叠工具栏按需挂载效果。 | 越小越好 |
| **7** | **浏览器 JS 内存占用（首屏 → 峰值）** | `MB` | 首屏完成时的 `performance.memory.usedJSHeapSize` $\to$ 滚动加载全过程中的最高 `usedJSHeapSize`（按 `1024 × 1024` 换算为 MB）。 | 越小越好 |
| **8** | **向上滚动时的帧间隔（P95）** | `ms` | 向上滚动与历史插入期间，相邻两帧 `requestAnimationFrame` 时间戳差值的 95 分位数。滿帧 60fps 对应约 `16.7 ms`；数值越高说明滚动越频繁卡顿。 | 越小越好（理想 `≈16.7 ms`） |
| **9** | **滚动时最长一帧** | `ms` | 向上滚动与历史分页加载期间，单次画面冻结的最长帧间隔（`max(Δt)`）。直接反映历史消息插入瞬间画面“卡死”的最坏体感。 | 越小越好 |
| **10** | **消息数据下载体积（压缩后，首屏 / 滚动后总计）** | `KB` | 拦截 `/api/sessions/:id/messages` 响应，按 Gzip 压缩后字节数统计：`首屏首次拉取体积 / 向上滚动触发历史分页后的累计总下载体积`（按 `1024` 换算为 KB）。 | 越小越好 |

DOM 检查同时验证目标路由、尾条目 ID、正文 hash 与可见区相交；不等于实际 Paint 或可交互。rAF 回调也不是精确 Paint。tail-sync 的 `isSyncingTail` true→false 通知包含网络等待，不是响应应用 CPU。两个 Long Task 桶可重叠；0 表示未观察到 ≥50ms 任务，不是零工作。body 前桶包含后续渐进挂载，不能标作纯首次 commit。

改动前无 profiler 的少量暖切换曾观察 A DOM 419.4ms／初始任务 416ms、B 363.0ms／362ms；改动后的重复样本低于这些单次观察，但不是对称 40 样本 A/B 前后实验。有限调用栈中 `reconcileInput` 约 6–7ms，React 首挂／JSX 构建占主要可归属成本，因此只实施 P2 首挂窗口，未引入跨会话 Store 池。重叠采样／原生未归属成本未相加。
